Public booking payment setup

Apply migrations/20261022_public_checkout_drafts.sql and migrations/20261030_public_checkout_reconciliation.sql in the Supabase SQL Editor before deploying the public checkout backend. The first migration requires the existing bookings and booking_payments tables; the second adds the reconciliation fields. The configured service role can access the staging table and finalization RPC; anonymous and signed-in clients cannot. The 20261031 migration is only needed to resume reconciliation for public Payment Intents created by the earlier direct-payment implementation.

Guest email addresses are checked for valid syntax, but email-code verification is not required to continue booking. Guests are reminded to enter an address they can access for booking updates.

The backend periodically checks due, active checkout sessions and Payment Intents directly with PayMongo, so a paid reservation can be finalized and acknowledged even if the guest closes the browser before returning and PayMongo's webhook is delayed or missed. The webhook remains the primary notification path. Checks are rate-limited per checkout, limited to 25 due drafts per worker pass, and can be disabled with `PUBLIC_CHECKOUT_RECONCILIATION_ENABLED=false`. Payment is still recorded only after PayMongo confirms the payment, amount, and currency.

New public bookings use PayMongo Hosted Checkout for the method selected on the booking page. Guests choose a payment method on The Villa and complete payment on PayMongo's secure page. This uses the backend `PAYMONGO_SECRET_KEY`; a PayMongo public key is not needed. Previously created public Payment Intents remain supported by status polling, webhooks, and reconciliation.

POST /public-bookings creates only a public_booking_checkouts draft. Checkout setup, failure, abandonment, expiration, and unpaid cancellation never insert bookings or booking_payments, send a booking acknowledgement, or enter admin booking reports. Drafts contain personal details and hashed access tokens, so RLS is enabled and access is limited to the backend service role.

The existing success return polls sync-payment. Both polling and the signed paid webhook retrieve the session or Payment Intent directly from PayMongo. Payment ID, amount, currency, and paid status must match before finalization. The SQL function locks the draft, checks for conflicting confirmed reservations, and inserts the booking and payment in one transaction. Concurrent/repeated calls do not duplicate bookings. Payment verification failures leave the draft available for retry. A cancellation return also checks PayMongo first: a confirmed payment is saved instead of being discarded.

A payment that conflicts with another reservation leaves the draft and payment evidence available for merchant review; it is not silently recorded as a successful booking. Drafts do not themselves reserve dates. Unpaid drafts remain separate from booking records; this change does not delete historical bookings or existing payment records. No scheduled deletion is added because a delayed payment webhook may still need its draft.

Local checks cover draft-only creation, unpaid/failed/expired attempts, cancellation, cancellation after payment, invalid amount/currency/session, token authorization, and atomic payment promotion using mocked storage and PayMongo. Run `python -m unittest discover -s tests -p 'test_*checkout.py'` from backend. Live PayMongo, SQL execution, and browser behavior require validation against the configured Supabase project after applying the migration.
