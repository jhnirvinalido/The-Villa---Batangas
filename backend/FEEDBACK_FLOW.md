# Existing booking-to-feedback workflow

## Inspection and scope

The existing public booking API, booking confirmation email, PayMongo verification, front-desk settlement, checkout endpoint, `guest_feedback` table contract, and `GuestFeedback.jsx` were reused. The form existed but had no React route. No trained NLP/Naive Bayes classifier, datasets, complaint extractor, frequency service, Gemini integration, or feedback admin API was present in the inspected repository. No database credentials/schema connection was available, so the SQL is based on the current repository's column contracts, not a claim to have inspected the deployed schema. No existing booking or feedback records are deleted.

## Deployment (required)

1. Apply `migrations/20261020_post_stay_feedback.sql` in Supabase SQL Editor, after the application's existing booking, booking-payments, and front-desk schemas. Review any deployed schema differences first. Existing `guest_feedback` fields must match the repository's API contract; the migration creates that existing source-of-truth table only when absent, adds identity/analysis columns, and preserves legacy rows. Existing duplicate feedback is retained; a locking trigger prevents additional duplicates. A unique booking index is added when existing data permits it.
2. Configure the existing `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, SMTP host/port/user/password/from/name, and publicly reachable HTTPS `FRONTEND_URL`. Reuse the existing logo path or `EMAIL_LOGO_PATH`. Service-role values remain backend-only.
3. Set a stable secret `FEEDBACK_TOKEN_SECRET` (a cryptographically generated value with at least 32 random bytes); the backend service-role key is the compatibility fallback. Do not rotate this secret while pending/uncertain invitations require retry or reconciliation. No new third-party package is required: email validation uses the `pydantic[email]` dependency already declared.
4. Restart FastAPI. `FEEDBACK_WORKER_ENABLED=true` is the default. The startup/shutdown worker follows the existing account-cleanup worker pattern. Every process may run it: database claims, leases, and booking uniqueness coordinate senders. Disable the worker only if a separately supervised process invokes `feedback_service.process_feedback_outbox` at least every minute.
5. Deploy React with a history fallback so `/feedback` opens directly. Allow `X-Feedback-Token` through reverse proxies/CORS. Disable or redact query-string access logs for legacy links; new invitation secrets use URL fragments and request headers, never request query strings. Do not log request bodies or feedback headers.

## Trigger and payment rules

The existing checkout transaction requires check-in, no remaining balance, and no pending QRPh settlement. At the user’s request, the checkout-date restriction is removed for testing; check-in retains its arrival-date rule. Feedback queueing happens only AFTER lifecycle persistence; failure never rolls back checkout. Repeated completed-checkout calls retry the idempotent queue operation. Existing PayMongo payment application and both front-desk settlement implementations also call it after persistence. A bounded periodic reconciliation sweep recovers interrupted hooks and completed stays whose payment becomes settled later through a supported update path; it does not weaken the checkout restrictions.

Eligibility requires completed/checked-out status, no cancellation/refund/invalid/void state, positive total, amount_paid covering total, remaining balance at most one cent, and confirmed ledger coverage from booking_payments plus front_desk_payments.room_balance_amount. Service charges are not mistaken for room-balance payments. Refunded/reversed ledger entries reject eligibility. A missing booking_payments table or unavailable validation fails closed. If the optional front_desk_payments table is absent, online ledger payments must still cover the entire room total; missing front-desk evidence is never invented. Python checks queueing and form access; SQL independently checks queueing, claims, submission, and admin review visibility. The worker checks again immediately before SMTP. Like any external email system, eligibility changes racing an already-in-flight SMTP handoff cannot recall a message; form access and submission recheck current eligibility.

## Persistent invitations and tokens

`feedback_invitation_outbox` is the only new invitation table; there is no second booking or feedback system. It has one row per booking and records creation, attempts, attempt time, next attempt, claim lease, stable Message-ID, SMTP acceptance time, state, and non-sensitive error codes.

A cryptographically random per-booking nonce is combined with the backend secret using domain-separated HMAC-SHA256. This yields a 256-bit capability token. The queue RPC atomically saves its hash in the existing bookings.feedback_token_hash, sets a 30-day expiry, and inserts the outbox row. The raw token is not stored; only the restricted nonce and the backend secret can reproduce it for retries. Repeated queueing never rotates the token or creates another invitation. SMTP retries reconstruct the same link. Previously sent links therefore are not accidentally invalidated.

The email is separate from `_send_booking_confirmation_email`, uses the existing SMTP configuration and inline PNG logo, and has the exact requested post-stay subject. It points to `/feedback?booking=UUID#token=CAPABILITY`. The guest needs no account. GET uses X-Feedback-Token, POST includes the token in its body, and both use `_require_feedback_booking`. Both verify the stored hash, expiry, revocation, completed stay and ledger-backed payment. POST checks again inside a transaction while locking the booking. A valid already-used link reports that feedback was received; a changed/revoked/expired token is rejected. Set feedback_token_revoked_at through privileged operations to revoke a link. Expired links are NOT automatically reissued or rotated. Operator reissue requires an explicit reviewed process; it is intentionally not exposed as a public action.

Outbox states: pending -> sending -> accepted; definite SMTP rejection/configuration failures -> retry with backoff; invalid eligibility/email/expiry -> suppressed. A timeout/disconnect after sending starts or a stale sender lease becomes uncertain. SMTP has no transactional exactly-once guarantee: uncertain handoffs require an operator to reconcile the stable Message-ID with the mail provider before marking accepted or retry. Never automatically reset accepted/uncertain rows. SMTP acceptance does not guarantee inbox delivery. If a finish-state database write fails, the lease prevents an immediate resend and later becomes uncertain. Successful checkout remains completed.

## Feedback storage and privacy

The existing star categories and recommendation answer are preserved. All five ratings are required, with overall 1–5 validation. Comments must contain at least 20 characters, four words, and varied textual content; the original trimmed text is retained in guest_feedback.comments. Private notes remain in their own restricted column and are excluded from the admin response and analysis contract. Written comments are not automatically public testimonials.

`hide_identity` is a display preference. The restricted booking association and original guest name/email are retained for verification. The admin API uses a strict whitelist: hidden records omit booking ID/reference and contact fields, display `Identity hidden`, and redact known name/contact/reference values plus email/phone patterns from displayed comments. Named records show the name and booking reference but not email/phone/private notes. Arbitrary free text cannot be promised to be anonymous; the form asks guests to avoid identifying details. This is pseudonymous/identity-hidden feedback, not complete anonymity. Existing administrators with direct database/service-role access are privileged operators and are outside the display-level privacy guarantee.

RLS and explicit privilege revocation deny direct anon/authenticated access to feedback, invitation state, rate counters, and all privileged RPCs. Guests interact through the token-checked FastAPI endpoints. Rate limits are database-backed per hashed peer-IP and method (60 GET or 12 POST per ten minutes), including invalid payload attempts. Configure trusted proxy forwarding correctly; do not trust arbitrary client X-Forwarded-For. Validation errors omit submitted input values. API responses use no-store; the feedback UI uses no-referrer and React renders text without HTML injection.

## Analysis integration boundary

New submissions are stored as analysis_status=awaiting_integration. `feedback_policy.analysis_input(row)` is the documented allowlisted future classifier contract: feedback ID, identity-redacted comments, and numeric ratings only. It excludes private_note, names, email, phone, booking references/IDs and tokens. Original text remains untouched for authorized evaluation/training; no permission for unrelated training is inferred. No synthetic model predictions, complaint frequencies, or Gemini recommendations are generated.

A future trained Multinomial Naive Bayes service should version its preprocessing/model, persist genuine sentiment results, extract aspect-level complaints, and count DISTINCT feedback IDs per negative complaint category. Only aggregates and redacted complaint evidence should be passed to Gemini; Gemini must not replace the classifier. Store actual provider/model versions, analysis failures, and recommendation review/action state when that service is implemented. The admin UI currently shows real review/rating aggregates and explicitly reports unavailable analysis.
